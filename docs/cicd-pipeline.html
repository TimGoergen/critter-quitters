Critter Quitters — CI/CD Pipeline Reference

Repository: github.com/TimGoergen/critter-quitters  ·  Pipeline file: .github/workflows/build.yml

What Is This and Where Does It Live?

This project uses GitHub Actions for its build and deployment pipeline. If you are familiar with Azure DevOps, think of GitHub Actions as Azure Pipelines built directly into GitHub — no separate service to configure, no project to link. The pipeline definition lives alongside the source code in the repository (.github/workflows/build.yml) and is versioned with it.

Azure DevOps equivalent GitHub Actions ≈ Azure Pipelines  ·  Workflow file ≈ azure-pipelines.yml  ·  Job ≈ Stage or Job  ·  Step ≈ Task  ·  GitHub Secrets ≈ Azure DevOps Library / Secret Variable Group

The pipeline runs entirely on GitHub-hosted runners — virtual machines that GitHub provisions, runs the job on, and discards automatically. You pay nothing and manage no build infrastructure. There are two runner types used:

  • ubuntu-latest — used for Godot exports and Firebase deployment (Linux VM)
  • windows-latest — used for Inno Setup packaging (Windows VM with Inno Setup 6 pre-installed)

Triggers — What Starts a Build?

Automatic Triggers

A build fires automatically whenever code is pushed to either of these branch patterns:

  • main — the primary branch; triggers the full pipeline including the Windows installer, GitHub release, and Firebase deployment.
  • feature/** — any branch whose name starts with feature/ (e.g. feature/new-unit-types); triggers only the export job and Firebase deployment. The Windows installer and GitHub release are skipped on feature branches.
Branch filter detail Pushing to any other branch name (e.g. hotfix/something, dev) does not trigger a build. Only main and branches matching feature/** are covered.

Manual Trigger

You can run the pipeline on demand without pushing any code. In GitHub Actions this is called a workflow dispatch — equivalent to clicking "Queue" on a pipeline in Azure DevOps.

  1. Open the repository on GitHub: github.com/TimGoergen/critter-quitters
  2. Click the Actions tab (top navigation).
  3. Click Build & Deploy in the left-hand workflow list.
  4. Click the Run workflow button on the right side of the page.
  5. Choose the branch to run against and click the green Run workflow button.

A manually-triggered run behaves identically to a push-triggered run on the same branch — the same jobs execute, the same artifacts are produced, and the same conditions apply (e.g. the installer and release jobs only run when the selected branch is main).

Job-by-Job Walkthrough

① Export — Windows + Android ubuntu-latest · runs on all branches

This is the core build job. It downloads the Godot engine, exports the game to two platforms, signs the Android APK, and uploads both outputs as pipeline artifacts (equivalent to Azure Pipelines' Publish Build Artifacts task).

  • 1
    Version stamping. Computes a 7-character short commit SHA (e.g. ecab1f6) and a zero-padded build number from the sequential GitHub run counter (e.g. 0042). These flow into file names and the Android version code/name throughout the rest of the pipeline.
  • 2
    Godot binary + export templates (cached). Downloads the Godot 4 Linux headless binary and the platform export templates from the official Godot GitHub releases page. Both are cached between runs using GitHub's cache service — equivalent to the Azure Pipelines Cache task — so subsequent builds skip the download entirely unless the Godot version changes.
  • 3
    Android signing setup. Decodes the release keystore from a base64 secret, injects the keystore password into export_presets.cfg, and writes the Android SDK and Java paths into Godot's editor settings file so Godot can locate the build tools.
  • 4
    Windows export. Runs Godot in headless (no GUI) mode to produce a single self-contained .exe file. The game code and all assets are embedded into the executable — no separate data directory is needed.
  • 5
    Android export + signing. Exports an unsigned APK, then signs it separately using apksigner from the Android build tools. Godot's own signing is disabled for this step due to a known Godot 4.5 bug (#109551) that causes the export to fail when the signing config is active in headless mode.
  • 6
    Artifact upload. Renames both output files to include the short SHA (e.g. critter_quitters_ecab1f6_win.exe) and uploads them as two named pipeline artifacts: windows-exe and android-apk. Downstream jobs download these artifacts rather than re-running the export.

② Windows Installer windows-latest · main branch only

Wraps the exported .exe in a proper Windows installer using Inno Setup 6, which is pre-installed on GitHub's Windows runners.

  • Downloads the windows-exe artifact from Job ①.
  • Calls ISCC.exe with the version string, source executable path, and output location passed as command-line defines.
  • The installer (build/setup.iss) configures a user-level install (no administrator rights required), LZMA compression, Start Menu shortcuts, an optional desktop icon, and a stable app GUID so Windows recognises upgrades and removes previous versions cleanly.
  • Uploads the resulting setup .exe as the windows-installer artifact.

③ Publish Release ubuntu-latest · main branch only · waits for ① and ②

Creates a GitHub Release — a versioned snapshot in the repository that bundles the downloadable artifacts. Think of it as a package version in Octopus Deploy's built-in feed, or a versioned drop in Azure Artifacts.

  • Downloads both the windows-installer and android-apk artifacts.
  • Creates a pre-release (not a full production release) tagged build-{sha} (e.g. build-ecab1f6), with installation instructions in the release body.
  • Attaches both files — the Windows installer .exe and the signed Android .apk — directly to the release as downloadable assets.

You can find all releases at: github.com/TimGoergen/critter-quitters/releases

④ Firebase Deploy ubuntu-latest · all branches · waits for ①

Pushes the signed APK to Firebase App Distribution, which functions similarly to Octopus Deploy pushing to an environment — it delivers the build to a designated group of testers and notifies them automatically.

  • The job checks whether the FIREBASE_APP_ID secret is configured. If it is not set, all subsequent steps are skipped and the job exits cleanly rather than failing the pipeline. This allows the pipeline to work before Firebase is set up.
  • Downloads the android-apk artifact from Job ①.
  • Uploads the APK to Firebase App Distribution targeting the testers group. The registered tester (goergen.tim@gmail.com) receives an install/update notification automatically.
  • Release notes are stamped automatically in the format:
    [feature/new-unit-types] ecab1f6: Add cloud-wipe scene transition on start screen

Versioning

Every build is stamped with two version identifiers computed from GitHub's environment:

  • Short SHA — first 7 characters of the Git commit hash (e.g. ecab1f6). Used in file names and the GitHub release tag so every artifact is traceable to the exact commit.
  • Build number — GitHub's sequential run counter, zero-padded to 4 digits (e.g. 0042). Used in the version string 0.0.0.0042, which appears in the Windows installer and in the Android version code/name. This counter never resets and always increases, so Windows and Android can always identify which build is newer.

Secrets and Configuration

Secrets are stored in GitHub Secrets, accessed via the repository's Settings → Secrets and variables → Actions page. This is equivalent to Azure DevOps' Library with secret variable groups — values are write-only in the UI, masked in all logs, and injected as environment variables at runtime.

Secret name What it contains Used by
ANDROID_KEYSTORE_BASE64 The Android release keystore file, base64-encoded Job ① — decoded to disk for APK signing
ANDROID_KEYSTORE_PASS Password for both the keystore and the signing key (they share a password) Job ① — injected into export_presets.cfg and passed to apksigner
FIREBASE_APP_ID Firebase Android App ID (format: 1:123…:android:abc…) Job ④ — identifies the app in Firebase. If absent, Job ④ skips gracefully.
FIREBASE_SERVICE_ACCOUNT_KEY Full JSON content of a GCP service account key with the Firebase App Distribution Admin role Job ④ — authenticates the upload to Firebase
Godot version upgrades The Godot version is set via the GODOT_VERSION environment variable at the top of build.yml (currently 4.5.1). When upgrading, change that value and then clear the Actions cache from the repository's Actions → Caches page. The next run will re-download the binary and export templates and rebuild the cache.

Viewing and Monitoring Runs

  • All runs: github.com/TimGoergen/critter-quitters/actions — equivalent to the Azure Pipelines runs list.
  • Live logs: Click any run, then any job, to see real-time step output. Equivalent to the Azure Pipelines job log view.
  • Re-run a failed job: On the run summary page, click Re-run failed jobs or Re-run all jobs. Equivalent to retrying a failed stage in Azure Pipelines.
  • Firebase builds: console.firebase.google.com → your project → App Distribution. Each build shows its release notes (branch, SHA, and commit message) and the tester delivery status.
